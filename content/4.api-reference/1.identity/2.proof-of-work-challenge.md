## `POST /{tenantId}/{country}/challenge?endpoint={endpointName}`

Before documenting individual Identity endpoints, this cross-cutting mechanism needs to be understood first: **every** write endpoint in this category (login, signup, verify, password reset/forgot, device, self-exclude, username setup, password change) is wrapped in a client-side retry helper (`withPoWRetry`) that reacts to a specific HTTP status by solving a proof-of-work challenge and retrying.

### How it works

1. The frontend calls the target endpoint normally (e.g. `POST /login`).
2. If the backend responds `HTTP 428 Precondition Required`, the frontend calls `POST /challenge?endpoint={endpointName}` to obtain a challenge.
3. The frontend brute-forces a `nonce` such that `SHA-256("{challenge}:{nonce}")` starts with `difficulty` leading zero hex characters.
4. The frontend retries the **original** request once, adding `X-PoW-Id` and `X-PoW-Nonce` headers.
5. This entire flow is skipped server-side (Nuxt SSR) — it only runs in the browser, since `crypto.subtle` PoW-solving requires a client runtime.

### `endpointName` values used today

| Consumer | `endpointName` sent |
| --- | --- |
| [Login](/api-reference/identity/login) | `login` |
| [Register](/api-reference/identity/register) | `signup` |
| [Verify OTP](/api-reference/identity/verify-otp) | `verify` |
| [Forgot Password](/api-reference/identity/forgot-password) | `password/forgot` |
| [Reset Password](/api-reference/identity/reset-password) | `password/reset` |
| [Device Registration](/api-reference/identity/device-registration) | `device` |
| [Self-Exclusion](/api-reference/identity/self-exclusion) | `profile/exclude` |
| [Setup Username](/api-reference/identity/setup-username) | `profile/username/setup` |
| [Change Password](/api-reference/identity/change-password) | `profile/password/change` |

::warning
These `endpointName` values are **logical labels**, not the literal request path (e.g. `password/forgot` label is used even though the real path is `/password/forgot`, and `profile/username/setup` is used even though the real path includes a `{userId}` segment). The backend's `/challenge` handler must recognize these exact label strings.
::

### Path parameters

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `tenantId` | `number` | Yes | Tenant/operator identifier. |
| `country` | `string` | Yes | Country code, e.g. `ke`. |

### Query parameters

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `endpoint` | `string` | Yes | One of the logical labels listed above, identifying which action is requesting a challenge. |

### Sample request

```bash
curl -X POST "https://api.touchvasgaming.com/1001/ke/challenge?endpoint=login"
```

### Sample response

```json
{
  "challenge_id": "chal_9f8e7d6c5b4a",
  "challenge": "a1b2c3d4e5f6...",
  "difficulty": 4,
  "expires_in": 120
}
```

### Response field reference

| Field | Type | Notes |
| --- | --- | --- |
| `challenge_id` | `string` | Echoed back as the `X-PoW-Id` header on the retried request. |
| `challenge` | `string` | The string the client hashes together with its guessed `nonce`. |
| `difficulty` | `number` | Number of leading hex zeroes the resulting SHA-256 hash must have. Higher = more client CPU time required. |
| `expires_in` | `number` | Seconds the client has to solve the challenge before it should be considered expired; used as the solving time budget (defaults to 120s client-side if absent). |

### Retried request headers

| Header | Value |
| --- | --- |
| `X-PoW-Id` | The `challenge_id` from the challenge response. |
| `X-PoW-Nonce` | The solved nonce, as a string. |

::note
The frontend retries **at most twice** and gives up if the backend keeps returning `428` — ensure a solvable challenge is issued reliably, or bot-protection will actively block legitimate users.
::

### Tenant-scoping notes for backend

- Challenge difficulty/expiry may be tuned per tenant, but a `challenge_id` issued under one tenant must not be redeemable against another tenant's endpoint.
