## Purpose

This section documents every **Wallet** endpoint currently consumed by the sportsbook Nuxt UI service, and defines the **multi-tenant contract** the backend team must implement going forward.

The client code for these endpoints lives in:

- `stores/walletStore.js`, `composables/useWallet.js` — bundled from the internal `wallet-ui-service` package, used across `pages/deposit.vue`, `pages/withdrawal.vue`, `pages/accounts_manager.vue`, `pages/index.vue`, `components/betting/BetSlip.vue`, `components/nav/*`, `components/Navbar.vue`, `components/accounts/Tab.vue`, `components/fixture/Freebet.vue`
- `pages/transaction.vue` — a **separate, legacy** direct implementation of transaction history and deposit initiation
- `composables/useAnalyticsIdentity.ts` — a third, independent direct call to the transactions endpoint, used only to count lifetime deposits for analytics

::note
This documentation exists so the backend team can implement the multi-tenant payload contract **exactly** as consumed by the frontend. Any deviation from the shapes below will break balances, deposits, withdrawals or transaction history without additional frontend changes.
::

## Important correction to the original endpoint categorization

::warning
The original brief classified the Bonus and Payment Gateway hosts as **"unused or configured only"**. Code review of the bundled `wallet-ui-service` package shows this is **incorrect** — both hosts are actively called, extensively, through the single `useWallet()` composable used throughout the app (balance, bonus balance, deposit, withdraw, payment channels, campaign redemption). They are documented here, alongside the Wallet host itself, because from the frontend's point of view they are all "the wallet." Recommend re-labelling those two hosts as in-use in the source-of-truth endpoint inventory.
::

## Current (single-tenant) base URLs

Three distinct backend hosts are involved, unified here under one neutral gateway domain:

```
https://api.touchvasgaming.com   (Wallet host — NUXT_PUBLIC_BASE_WALLET_URL)
https://api.touchvasgaming.com   (Bonus host — NUXT_PUBLIC_BASE_BONUS_URL)
https://api.touchvasgaming.com   (Payment Gateway host — NUXT_PUBLIC_PAYMENT_GW_URL)
```

## Required change: tenant scoping

Same platform-wide rule as the rest of the API (see the [Fixture / Sports overview](/api-reference/fixture-sports) for the full contract): every endpoint **must** accept `/{tenantId}/{country}/` as the **first two path segments** — mandatory, no exceptions, regardless of which of the three legacy hosts an endpoint used to live on.

```diff
- GET https://api.touchvasgaming.com/balance?lang=en&country_code=ke
+ GET https://api.touchvasgaming.com/1001/ke/balance?lang=en
```

::warning
Query-parameter usage for `lang`/`country_code` is **inconsistent across consumers** today:

- The `wallet-ui-service` package sends `lang`+`country_code` on `balance`, `transactions`, `get/settings`, `bonus/balance`, `deposit`, `deposit/status`, `withdraw`, `profile/channels` (list/create) — but only `lang` (no `country_code`) on `verify`/`delete` channel — and **neither** on `campaign/redeem` or `resend` OTP.
- `pages/transaction.vue`'s legacy direct calls to `transactions` and `deposit/initiate` send **neither** `lang` nor `country_code`.
- `composables/useAnalyticsIdentity.ts`'s direct call to `transactions` also sends **neither**.

Under the new standard, all of the above must move to the mandatory `/{tenantId}/{country}/` path prefix and drop `country_code` entirely; `lang` remains a query parameter only where already used.
::

## Endpoint index

| # | Method | Path (multi-tenant) | Purpose |
| --- | --- | --- | --- |
| 1 | `GET` | `/{tenantId}/{country}/balance` | Main + bonus wallet balance |
| 2 | `GET` | `/{tenantId}/{country}/bonus/balance` | Detailed bonus balance and active/pending bonuses |
| 3 | `GET` | `/{tenantId}/{country}/transactions` | Paginated transaction history |
| 4 | `GET` | `/{tenantId}/{country}/get/settings` | Deposit/withdrawal limits |
| 5 | `POST` | `/{tenantId}/{country}/deposit` **or** `/{tenantId}/{country}/deposit/initiate` | Initiate a deposit — **two competing implementations, see below** |
| 6 | `POST` | `/{tenantId}/{country}/deposit/status` | Check the status of a previously initiated deposit |
| 7 | `POST` | `/{tenantId}/{country}/withdraw` | Withdraw funds to a payment channel |
| 8 | `GET` / `POST` | `/{tenantId}/{country}/profile/channels` | List / add a payment channel (account) |
| 9 | `GET` | `/{tenantId}/{country}/profile/channels/resend/{id}` | Resend the OTP for a pending channel verification |
| 10 | `POST` | `/{tenantId}/{country}/profile/channels/verify/{id}` | Verify a payment channel with an OTP |
| 11 | `DELETE` | `/{tenantId}/{country}/profile/channels/{id}` | Remove a payment channel |
| 12 | `POST` | `/{tenantId}/{country}/campaign/redeem` | Redeem a bonus campaign code |

Each endpoint is documented in its own page with path/query parameters, headers, sample requests and precise sample responses matching the frontend TypeScript contracts.

## Common conventions across all endpoints

- **`lang`**: locale code, e.g. `en`. Sent as a query parameter where the frontend currently uses it (see per-endpoint warnings where it is missing today).
- **`{country}`**: lowercase ISO-like country code, e.g. `ke`. Now a **mandatory path segment**, immediately after `{tenantId}` — replaces the old `country_code` query parameter used inconsistently across consumers.
- **Authentication**: Every endpoint in this category requires an `api-key` header carrying the user's session/auth token — the wallet is always tied to an authenticated user. A `401` response is treated uniformly by the frontend as `"Unauthorized - session expired"`.
- **Content type**: All requests/responses are `application/json`.
- **Errors**: The frontend reads `error_message` from the JSON error body (`fetchError.data?.error_message`), falling back to a generic per-action message. Standardize on `error_message`; see the [recommended error envelope](/api-reference/fixture-sports#recommended-error-envelope).

### Tenant-scoping notes for backend (apply to all endpoints in this category)

- Balances, bonuses, deposit/withdrawal limits, payment channels and transaction history are all scoped to **the authenticated user within the requesting tenant** — validate the user belongs to `tenantId` and reject cross-tenant requests with `403 Forbidden`.
- Money-moving endpoints (`deposit`, `withdraw`, `campaign/redeem`, channel create/verify/delete) are hard-to-reverse operations — ensure idempotency and tenant-aware audit logging.
