## `POST /{tenantId}/{country}/deposit` — and a second, competing `POST /{tenantId}/{country}/deposit/initiate`

::warning
**Deposit initiation is implemented twice, on two different hosts, with two different payloads.** The backend team must decide which is authoritative and communicate the migration path:

**A. `stores/walletStore.js` → `deposit()`** (bundled package; used by `pages/deposit.vue`) — calls `POST /deposit` on the **Payment Gateway** host:

```json
{
  "amount": 500,
  "account_id": 2000000019,
  "account_number": "2547XXXXXXXX",
  "account_type": 1,
  "payment_channel_id": 3,
  "finger_print": "a1b2c3d4-fingerprint-hash"
}
```

Success is `HTTP 201` or `202`. On success, the frontend re-fetches [Balance](/api-reference/wallet/balance) and [Bonus Balance](/api-reference/wallet/bonus-balance).

**B. `pages/transaction.vue` → `userDeposit()`** (legacy, direct) — calls `POST /deposit/initiate` on the **Wallet** host:

```json
{
  "amount": 500
}
```

No `account_id`, `account_number`, `account_type`, `payment_channel_id` or `finger_print` — and no re-fetch of balance afterwards. Success is any non-error HTTP response.

**These cannot both be the "current" contract long-term — recommend backend and frontend teams align on consumer A's richer payload (channel-based deposits) as the target, and plan removal of consumer B.**
::

### Path parameters

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `tenantId` | `number` | Yes | Tenant/operator identifier. |
| `country` | `string` | Yes | Country code, e.g. `ke`. |

### Query parameters

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `lang` | `string` | `en` | Locale code. Sent by consumer A only. |

### Headers

| Header | Value | Required |
| --- | --- | --- |
| `Content-Type` | `application/json` | Yes |
| `api-key` | User's auth token | Yes |

### Request body (consumer A — recommended)

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `amount` | `number` | Yes | Deposit amount, validated client-side against [Wallet Settings](/api-reference/wallet/wallet-settings). |
| `account_id` | `number` | No | Operator/merchant account identifier. |
| `account_number` | `string` | No | The paying account (e.g. phone number) for the selected channel. |
| `account_type` | `number` | No | Numeric account type code (channel-specific). |
| `payment_channel_id` | `number` | No | The channel `id` from [Payment Channels](/api-reference/wallet/payment-channels). |
| `finger_print` | `string` | No | Visitor fingerprint (e.g. FingerprintJS `visitorId`) for fraud detection. |

### Sample request

```bash
curl -X POST "https://api.touchvasgaming.com/1001/ke/deposit?lang=en" \
  -H "Content-Type: application/json" \
  -H "api-key: <user-auth-token>" \
  -d '{
    "amount": 500,
    "account_number": "2547XXXXXXXX",
    "account_type": 1,
    "payment_channel_id": 3
  }'
```

### Sample response

```json
{
  "data": "Please complete the payment on your phone.",
  "iframe": false,
  "link": "https://provider.example.com/pay/session/abc123"
}
```

### Response field reference

| Field | Type | Notes |
| --- | --- | --- |
| `data` | `string` | Shown to the user as an instructional/status message. |
| `iframe` | `boolean` | `true` if `link` should be opened in an embedded iframe rather than a redirect. |
| `link` | `string` | Payment provider URL, when the flow requires one (e.g. card/redirect-based channels). |

### Tenant-scoping notes for backend

- Deposit limits, available channels and fraud checks (`finger_print`) must be evaluated per-tenant.
